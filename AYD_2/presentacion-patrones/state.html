Patrón de comportamiento · GoF

State

«Permite que un objeto altere su comportamiento cuando cambia su estado interno. El objeto parecerá cambiar de clase.»

Implementado en reservas/estados.py; el contexto es la clase Reserva de reservas/models.py.

Para entenderlo · la analogía del dron

Un dron tiene botones que a veces no hacen nada

Probalo: apretá los botones en el orden que quieras. El botón Aterrizar está siempre ahí — pero sólo sirve si el dron está volando. El dron sabe en qué estado está, y él decide qué se puede hacer.

Estado del dron: EN TIERRA

Apretá un botón para empezar. Probá a propósito uno que no toque — por ejemplo, aterrizar un dron que está apagado.

En el dron

«No puedo aterrizar: estoy en tierra.» El dron no se rompe ni obedece a medias: avisa que esa acción no aplica en el estado en el que está.

≡

En AutoRent

«No se puede aceptar una reserva en estado EN_RENTA.» Exactamente el mismo mensaje, generado por la misma idea: cada estado sabe qué se le puede pedir.

Cambiá «dron» por «reserva», y «volando» por «propuesta»: es el mismo diseño. Lo que sigue es cómo se ve eso escrito en Python.

El problema

Cinco operaciones con la misma cadena de if

Una reserva se puede proponer, aceptar, rechazar, entregar y finalizar. Sin el patrón, cada una de esas cinco operaciones necesita su propio condicional sobre el campo estado:

class Reserva:
    def aceptar(self):
        if self.estado == 'PROPUESTA': ...
        else: raise Error('no se puede')

    def rechazar(self, motivo):
        if self.estado == 'PROPUESTA': ...
        else: raise Error('no se puede')

    def entregar(self):   if self.estado == 'ACEPTADA': ...
    def finalizar(self):  if self.estado == 'EN_RENTA': ...
    def proponer(self, h): if self.estado == 'SOLICITADA': ...

Regla dispersa

Para saber qué se puede hacer en el estado PROPUESTA hay que leer los cinco métodos.

Cerrado a extensión

Agregar un estado obliga a tocar los cinco. Lo contrario al principio abierto/cerrado.

Fácil de romper

Nada garantiza que las cinco cadenas sean coherentes. Basta olvidar un else para permitir una transición ilegal.

Aplicabilidad, textual del GoF: «Úsese State cuando las operaciones tienen condicionales grandes y de varias partes que dependen del estado del objeto […] y frecuentemente varias operaciones contienen la misma estructura condicional.» Es literalmente este caso.

La solución

Un estado, una clase

Reserva es el Context; EstadoReserva es el State; las seis clases de abajo son los ConcreteState.

El flujo, visto como autómata

La máquina de estados de una reserva

En verde, el efecto colateral sobre el vehículo que cada transición dispara. RECHAZADA y FINALIZADA son estados terminales: no aceptan ninguna transición.

El código real · 1 de 2

La clase abstracta que prohíbe todo

# reservas/estados.py
class EstadoReserva(ABC):
    codigo = None

    @staticmethod
    def crear(codigo):
        # del código persistido al ConcreteState
        return _ESTADOS[codigo]()

    def proponer(self, reserva, horario): self._invalido('proponer')
    def aceptar(self, reserva):           self._invalido('aceptar')
    def rechazar(self, reserva, motivo): self._invalido('rechazar')
    def entregar(self, reserva):          self._invalido('entregar')
    def finalizar(self, reserva):         self._invalido('finalizar')

    def _invalido(self, accion):
        raise ValidationError(
            f'No se puede {accion} una reserva en estado {self.codigo}.')

La decisión de diseño: la clase base no declara métodos abstractos vacíos — declara métodos que lanzan excepción. El comportamiento por omisión es «esta transición es ilegal».

Consecuencia directa: un estado concreto sólo escribe los métodos que sí puede ejecutar. Todo lo demás queda prohibido sin escribir una sola línea. Un estado terminal completo son tres líneas:

class Rechazada(EstadoReserva):
    """Estado terminal: no acepta ninguna transición."""
    codigo = 'RECHAZADA'

Las reglas del negocio dejaron de estar repartidas en condicionales: ahora se leen en la definición de cada clase — lo que una clase implementa es lo que ese estado permite.

El código real · 2 de 2

El estado concreto y el contexto

ConcreteState — la clase que sabe qué significa aceptar cuando la reserva está propuesta:

class Propuesta(EstadoReserva):
    codigo = 'PROPUESTA'

    def aceptar(self, reserva):
        reserva.precio_dia_aplicado = reserva.vehiculo.precio_dia
        reserva.descuento_aplicado  = reserva.plan.descuento
        reserva.precio_total = reserva.calcular_total()
        reserva.vehiculo.estado = Vehiculo.Estado.RESERVADO
        reserva.vehiculo.save()
        reserva.cambiar_estado(Aceptada())

    def rechazar(self, reserva, motivo):
        if not motivo or not motivo.strip():
            raise ValidationError('Debe indicar el motivo del rechazo.')
        reserva.motivo_rechazo = motivo
        reserva.vehiculo.estado = Vehiculo.Estado.DISPONIBLE
        reserva.vehiculo.save()
        reserva.cambiar_estado(Rechazada())

Context — las cinco operaciones de Reserva sólo delegan:

class Reserva(models.Model):
    estado = models.CharField(choices=Estado.choices)

    @property
    def estado_actual(self) -> EstadoReserva:
        return EstadoReserva.crear(self.estado)

    def cambiar_estado(self, nuevo: EstadoReserva):
        self.estado = nuevo.codigo
        self.save()

    def proponer(self, horario): self.estado_actual.proponer(self, horario)
    def aceptar(self):           self.estado_actual.aceptar(self)
    def rechazar(self, motivo): self.estado_actual.rechazar(self, motivo)
    def entregar(self):         self.estado_actual.entregar(self)
    def finalizar(self):        self.estado_actual.finalizar(self)

El punto a destacar en la defensa: en el Context no quedó ni un solo if sobre el estado. Cada método es una línea que delega. El objeto de estado se materializa desde el código persistido en la columna estado y se descarta después.

Patrón y persistencia

La misma regla, en dos capas

Las reglas del patrón no viven sólo en Python: están espejadas en los CHECK del esquema. Si alguien insertara por SQL directo, la base también las hace cumplir.

Constraint en el DDLRegla equivalente en el patrónDónde se aplica

chk_motivo_si_rechazada No se puede rechazar sin motivo: se valida antes de cambiar de estado. Propuesta.rechazar()
chk_horario_si_propuesta Se asigna horario_propuesto antes de pasar a PROPUESTA. Solicitada.proponer()

Efecto colateral controlado

Cada transición además sincroniza el estado del vehículo. Al estar dentro de la clase de estado, es imposible cambiar la reserva y olvidar el vehículo.

Por qué se persiste un código y no el objeto

El objeto de estado no tiene datos propios, sólo comportamiento. Por eso se guarda únicamente el discriminador y el ConcreteState se reconstruye cuando se necesita — el consejo del GoF para estados sin atributos.
