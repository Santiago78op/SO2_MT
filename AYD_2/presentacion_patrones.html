El recorrido de una renta, y quién actúa en cada paso

El enunciado define tres roles. La lógica interesante ocurre entre cliente y agente: ninguno de los dos puede avanzar solo, se van pasando el turno. Eso es lo que el patrón State vigila.

Los tres patrones se concentran en el paso 3, cuando el cliente acepta: es el único momento en que se calcula dinero.

Del clic del usuario a la clase de estado

Django organiza el código en MTV: plantilla, vista y modelo. Los patrones viven en el modelo, no en la vista. La vista sólo traduce el clic en una llamada de negocio y muestra el error si lo hay.

La vista, completa
# reservas/views.py
@login_required
@require_POST
@transaction.atomic
def aceptar_reserva(request, reserva_id):
    if not es_cliente(request.user):
        return HttpResponseForbidden('Solo el cliente...')
    reserva = get_object_or_404(
        Reserva.objects.select_for_update(),  # bloqueo de fila
        pk=reserva_id, cliente__usuario=request.user)
    try:
        reserva.aceptar()            # ← la regla vive aquí
        messages.success(request, 'Reserva aceptada.')
    except ValidationError as error:
        messages.error(request, ' '.join(error.messages))
    return redirect('reservas:detalle', reserva_id=reserva_id)
Los dos puntos a decir en voz alta La vista tiene una sola línea de negocio: si cambia la regla de qué estado puede aceptar, la vista no se toca. Y con transaction.atomic + select_for_update(), dos peticiones simultáneas no pueden avanzar la misma reserva.

State · el problema

Cinco operaciones, la misma cadena de if

Sin el patrón
class Reserva:
    def aceptar(self):
        if self.estado == 'PROPUESTA':
            ...
        else:
            raise Error('no se puede')

    def rechazar(self, motivo):
        if self.estado == 'PROPUESTA':
            ...
        else:
            raise Error('no se puede')

    def entregar(self):
        if self.estado == 'ACEPTADA': ...
    def finalizar(self):
        if self.estado == 'EN_RENTA': ...
    def proponer(self, horario):
        if self.estado == 'SOLICITADA': ...
Por qué duele
  • La regla de negocio queda repartida en cinco métodos. Para saber qué se puede hacer en el estado PROPUESTA hay que leerlos todos.
  • Agregar un estado nuevo obliga a tocar los cinco. Es exactamente lo contrario al principio abierto/cerrado.
  • Nada garantiza que las cinco cadenas de condicionales sean coherentes entre sí. Basta olvidar un else para permitir una transición ilegal.
Aplicabilidad — GoF «Úsese State cuando las operaciones tienen condicionales grandes y de varias partes que dependen del estado del objeto […] y frecuentemente varias operaciones contienen la misma estructura condicional.» Gamma, Helm, Johnson & Vlissides — Design Patterns, patrón State.

Es literalmente el caso: cinco operaciones con la misma estructura condicional sobre el campo estado.

State · el código real

La clase abstracta que prohíbe todo

# reservas/estados.py
class EstadoReserva(ABC):
    codigo = None

    @staticmethod
    def crear(codigo):
        # del código persistido al ConcreteState
        return _ESTADOS[codigo]()

    def proponer(self, reserva, horario): self._invalido('proponer')
    def aceptar(self, reserva):           self._invalido('aceptar')
    def rechazar(self, reserva, motivo): self._invalido('rechazar')
    def entregar(self, reserva):          self._invalido('entregar')
    def finalizar(self, reserva):         self._invalido('finalizar')

    def _invalido(self, accion):
        raise ValidationError(
            f'No se puede {accion} una reserva '
            f'en estado {self.codigo}.')
Código tal cual está en el repositorio (simplificado sólo en el salto de línea de las cinco firmas).
La decisión de diseño La clase base no declara métodos abstractos vacíos. Declara métodos que lanzan excepción. El comportamiento por omisión es «esta transición es ilegal».

Consecuencia directa: un estado concreto sólo escribe los métodos que sí puede ejecutar. Todo lo demás queda prohibido sin escribir una sola línea.

class Rechazada(EstadoReserva):
    """Estado terminal: no acepta ninguna transición."""
    codigo = 'RECHAZADA'

Tres líneas y el estado queda completamente blindado: las cinco operaciones heredadas rechazan.

Qué se ganó Las reglas del negocio dejaron de estar repartidas en condicionales. Ahora se leen en la definición de cada clase: lo que una clase implementa es lo que ese estado permite.

class Propuesta(EstadoReserva):
    codigo = 'PROPUESTA'

    def aceptar(self, reserva):
        reserva.precio_dia_aplicado = reserva.vehiculo.precio_dia
        reserva.descuento_aplicado  = reserva.plan.descuento
        reserva.precio_total = reserva.calcular_total()
        reserva.vehiculo.estado = Vehiculo.Estado.RESERVADO
        reserva.vehiculo.save()
        reserva.cambiar_estado(Aceptada())

    def rechazar(self, reserva, motivo):
        if not motivo or not motivo.strip():
            raise ValidationError('Debe indicar el motivo.')
        reserva.motivo_rechazo = motivo
        reserva.vehiculo.estado = Vehiculo.Estado.DISPONIBLE
        reserva.vehiculo.save()
        reserva.cambiar_estado(Rechazada())
Context — reservas/models.py
class Reserva(models.Model):
    estado = models.CharField(choices=Estado.choices)

    @property
    def estado_actual(self) -> EstadoReserva:
        return EstadoReserva.crear(self.estado)

    def cambiar_estado(self, nuevo: EstadoReserva):
        self.estado = nuevo.codigo
        self.save()

    # las cinco operaciones sólo DELEGAN
    def proponer(self, horario): self.estado_actual.proponer(self, horario)
    def aceptar(self):           self.estado_actual.aceptar(self)
    def rechazar(self, motivo): self.estado_actual.rechazar(self, motivo)
    def entregar(self):         self.estado_actual.entregar(self)
    def finalizar(self):        self.estado_actual.finalizar(self)
El punto a destacar En el Context no quedó ni un solo if sobre el estado. Cada método es una línea que delega. El objeto de estado se materializa desde el código persistido en la columna estado y se descarta después.

La misma regla, en dos capas

Las reglas del patrón no viven sólo en Python: están espejadas en los CHECK del esquema. Si alguien insertara por SQL directo, la base también las hace cumplir.

Constraint en el DDLRegla equivalente en el patrónDónde se aplica
chk_estado_reserva Sólo existen los seis códigos que conoce el diccionario _ESTADOS. EstadoReserva.crear()
chk_motivo_si_rechazada No se puede rechazar sin motivo: se valida antes de cambiar de estado. Propuesta.rechazar()
chk_horario_si_propuesta Se asigna horario_propuesto antes de pasar a PROPUESTA. Solicitada.proponer()
Efecto colateral controlado Cada transición además sincroniza el estado del vehículo (RESERVADO, EN_RENTA, DISPONIBLE). Al estar dentro de la clase de estado, es imposible cambiar la reserva y olvidar el vehículo.
Por qué se persiste un código y no el objeto El objeto de estado no tiene datos propios, sólo comportamiento. Por eso se guarda únicamente el discriminador estado y el ConcreteState se reconstruye cuando se necesita. Es el consejo del GoF: los objetos de estado sin atributos pueden compartirse.

Strategy · problema y solución

Tres formas de cobrar la misma renta

El enunciado pide planes de renta. Cada plan cobra distinto: por día, por semana con descuento, por mes con descuento.

Si no se usara el patrón Reserva.calcular_total() tendría un if por plan, y agregar un «Plan quincenal» obligaría a modificar la clase Reserva — una clase que no tiene nada que ver con fórmulas de precio.
Con el patrón Cada fórmula es una clase con un solo método. Reserva recibe una estrategia y la ejecuta sin saber cuál es. Agregar un plan nuevo es agregar una clase.
Aplicabilidad — GoF «Úsese Strategy cuando muchas clases relacionadas difieren sólo en su comportamiento» y «cuando se necesitan distintas variantes de un algoritmo».

Una fórmula, una clase

# reservas/calculos.py
class CalculoPlan(ABC):
    """Strategy: interfaz común a todas
    las formas de calcular el total."""

    @abstractmethod
    def calcular_total(self, reserva) -> Decimal: ...


class TarifaDiaria(CalculoPlan):
    def calcular_total(self, reserva) -> Decimal:
        return reserva.vehiculo.precio_dia * reserva.cantidad_dias


class TarifaSemanal(CalculoPlan):
    def calcular_total(self, reserva) -> Decimal:
        precio = reserva.vehiculo.precio_dia
        semanas, sueltos = divmod(reserva.cantidad_dias, 7)
        factor = Decimal('1') - (reserva.plan.descuento / 100)
        return (semanas * 7 * precio * factor) + (sueltos * precio)
TarifaMensual es idéntica cambiando 7 por 30.
Cómo la usa el Context
# reservas/models.py — clase Reserva
def calcular_total(self) -> Decimal:
    estrategia = self.plan.calculo() if self.plan else TarifaDiaria()
    return estrategia.calcular_total(self)

Factory Method · problema y solución

¿Quién decide cuál Strategy se usa?

Strategy resolvió cómo se calcula. Queda un hueco: el plan que eligió el cliente está guardado en la base como un texto ('SEMANAL'). Alguien tiene que traducirlo a un objeto.

El riesgo Si esa traducción la hiciera Reserva, el Context volvería a conocer los nombres de las clases concretas — justo lo que Strategy vino a evitar.
La solución PlanRenta es el Creator: su método calculo() recibe el discriminador que él mismo tiene persistido y devuelve el producto concreto.
El código
# reservas/models.py
class PlanRenta(models.Model):
    _PRODUCTOS = {
        Calculo.DIARIA:  TarifaDiaria,
        Calculo.SEMANAL: TarifaSemanal,
        Calculo.MENSUAL: TarifaMensual,
    }
    calculo_codigo = models.CharField(choices=Calculo.choices)

    # ---------- FACTORY METHOD ----------
    def calculo(self) -> CalculoPlan:
        return self._PRODUCTOS[self.calculo_codigo]()
El Creator conoce a los productos; Reserva no.

Pregunta clásica

Si el diagrama es igual, ¿por qué son dos patrones?

State y Strategy tienen la misma estructura: un contexto que delega en una jerarquía de clases. Lo que los separa es la intención, y eso se ve en el proyecto.

State — reservas/estados.pyStrategy — reservas/calculos.py
Qué encapsula Una situación del objeto y las transiciones legales desde ella. Un algoritmo completo e independiente.
Quién elige Lo elige el propio patrón: Propuesta.aceptar() decide que el siguiente estado es Aceptada. Lo elige el cliente / la configuración: el plan que el usuario seleccionó.
Se conocen entre sí Sí. Propuesta nombra a Aceptada y a Rechazada. No. TarifaSemanal no sabe que existe TarifaMensual.
Cambia solo Sí, durante la vida del objeto. Una reserva recorre varios estados. No. Se fija al crear la reserva y no cambia.
Frase resumen «El objeto está en un estado.» «El objeto usa un algoritmo.»
Cómo se responde en una línea Una reserva pasa de SOLICITADA a PROPUESTA sola, por efecto de una operación. Nunca «pasa» de TarifaDiaria a TarifaSemanal: esa se elige una vez y se queda.
State frente a Strategy16
Preparación para la defensa

Preguntas que conviene tener respondidas

¿Ese Factory Method es el del GoF? Es la variante que el propio GoF llama factory method parametrizado: un solo método recibe un identificador y devuelve el producto, en lugar de una subclase por producto. Se eligió así porque el discriminador ya existía como columna en la base (plan_renta.calculo_codigo) y crear una subclase de PlanRenta por cada plan habría duplicado la tabla sin ganar nada.
¿Y EstadoReserva.crear()? Es el mismo mecanismo aplicado a los estados: traduce el código persistido al ConcreteState. Es la pieza que conecta la base de datos relacional con el patrón, porque una tabla no puede guardar un objeto de comportamiento.
¿Qué pasa si intento una transición ilegal? Se lanza ValidationError con el mensaje «No se puede aceptar una reserva en estado EN_RENTA». La vista lo captura y lo muestra como mensaje de error. Nunca se corrompe el dato: las operaciones críticas corren dentro de transaction.atomic.
¿Cómo agregarían un plan quincenal? Tres pasos, sin tocar Reserva ni las vistas: crear la clase TarifaQuincenal(CalculoPlan), agregar la entrada al diccionario _PRODUCTOS y sembrar la fila en plan_renta. Ese es el argumento concreto de por qué los patrones valieron la pena.
¿Un estado nuevo? Una clase que hereda de EstadoReserva, sobreescribe sólo lo legal y se registra en _ESTADOS. Las clases existentes no se modifican.
