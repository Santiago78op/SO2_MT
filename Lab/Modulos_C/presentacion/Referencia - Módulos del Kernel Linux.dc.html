Módulos del kernel Linux

Referencia de estudio · lenguaje C · Pop!_OS con kernel 6.x

Documento acompañante de la presentación «Módulos del kernel Linux»

1. Qué es un módulo y por qué existe

Un módulo del kernel es un objeto ELF con extensión .ko que el kernel enlaza dentro de su propio espacio de direcciones mientras el sistema está en ejecución. No es un proceso, no es una biblioteca compartida y no está aislado: desde el momento en que se carga, su código es kernel con todos los privilegios del kernel.

Linux es un kernel monolítico modular. Monolítico porque todos los subsistemas comparten un mismo espacio de direcciones privilegiado y se llaman entre sí con llamadas de función directas. Modular porque ese espacio se puede extender y reducir en caliente. Las tres razones prácticas para que exista este mecanismo:

  • Se carga en memoria únicamente el código que esa máquina concreta necesita.
  • El ciclo de desarrollo se reduce a segundos: compilar, cargar, probar, descargar.
  • Un driver de terceros se puede instalar sin recompilar ni reemplazar el kernel de la distribución.

La contrapartida es la fragilidad: una desreferencia nula en espacio de usuario mata un proceso; en un módulo produce un oops —y con frecuencia un pánico que se lleva todo el sistema. Por eso el desarrollo se hace en una máquina virtual.

2. Reglas del entorno del kernel

Programar en C dentro del kernel es C, pero con otro contrato. Las diferencias que más rápido se notan:

Aspecto Espacio de usuario Espacio del kernel
Biblioteca estándar glibc completa solo la API interna del kernel
Memoria dinámica malloc / free kmalloc / kzalloc / kfree
Salida de texto printf printk / pr_info / dev_info
Pila megabytes, crece 8–16 KB fijos por hilo
Coma flotante disponible se evita (coste de contexto FPU)
Fallo típico segfault del proceso oops o kernel panic

4. Ciclo de vida y herramientas

Un módulo pasa por cuatro estados: compilado en disco, cargado, en uso y descargado. Al cargarlo, el kernel resuelve sus símbolos externos, comprueba el vermagic —la huella de la versión y la configuración del kernel contra la que se compiló—, valida la firma si es obligatoria y ejecuta la función de inicialización. Al descargarlo ejecuta la función de salida, pero solo si el contador de referencias es cero.

La regla que evita la mayoría de los problemas: la función de salida deshace lo que hizo la de entrada, en orden inverso. Todo recurso no liberado queda ocupado hasta el reinicio.

Herramienta Qué hace
lsmod Lista los módulos residentes, su tamaño y sus usuarios. Formatea /proc/modules.
modinfo Inspecciona un .ko sin cargarlo: autor, licencia, descripción, parámetros, dependencias, vermagic y firma.
insmod Carga un archivo por ruta exacta. No resuelve dependencias: si falta un símbolo, falla.
modprobe Carga por nombre desde /lib/modules/$(uname -r), arrastrando dependencias. Con -r descarga en cascada; con -n -v muestra qué haría.
depmod Reconstruye modules.dep y los mapas de alias. Obligatorio tras instalar un módulo nuevo.
rmmod Descarga un módulo concreto. Falla si su contador de referencias no es cero.

Rutas relevantes del sistema

/lib/modules/$(uname -r)/kernel/      módulos que trae la distribución
/lib/modules/$(uname -r)/extra/       módulos externos instalados
/lib/modules/$(uname -r)/build/       headers y kbuild (enlace simbólico)
/lib/modules/$(uname -r)/modules.dep  grafo de dependencias
/etc/modules-load.d/*.conf            módulos a cargar en el arranque
/etc/modprobe.d/*.conf                opciones, alias y listas negras
/proc/modules                         estado en vivo
/sys/module/<nombre>/parameters/      parámetros expuestos

5. El módulo mínimo

No hay main(). Hay dos puntos de entrada declarados con macros: uno se ejecuta al cargar y otro al descargar.

/* hello.c */
#include <linux/module.h>
#include <linux/init.h>

static int __init hello_init(void)
{
        pr_info("hello: cargado\n");
        return 0;               /* 0 = éxito; negativo = errno */
}

static void __exit hello_exit(void)
{
        pr_info("hello: descargado\n");
}

module_init(hello_init);
module_exit(hello_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Tu nombre");
MODULE_DESCRIPTION("Módulo de ejemplo");
MODULE_VERSION("1.0");

Listado 3 — Módulo mínimo completo.

  • __init marca la función como desechable: el kernel libera su memoria en cuanto termina la carga. __exit permite descartarla cuando el módulo se compila estáticamente.
  • Devolver un errno negativo desde init aborta la carga: el módulo no queda residente. Si ya reservaste recursos, libéralos antes de retornar.
  • MODULE_LICENSE es obligatoria en la práctica: sin una licencia compatible con GPL el kernel se marca como tainted y te niega el acceso a los símbolos exportados con EXPORT_SYMBOL_GPL.

6. Compilar con kbuild

El Makefile del módulo no compila nada por sí mismo: delega en el sistema de construcción del árbol del kernel, indicándole con M= dónde está el código externo.

# Makefile — las recetas van indentadas con TABULADOR
obj-m += hello.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD  := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

install:
	$(MAKE) -C $(KDIR) M=$(PWD) modules_install
	depmod -a

.PHONY: all clean install

Listado 4 — Makefile de un módulo fuera del árbol del kernel.

Para un módulo con varios archivos fuente, el nombre del módulo y el de los objetos se declaran por separado:

obj-m         += midriver.o
midriver-objs := core.o sysfs.o chardev.o
ccflags-y     += -Wall -DDEBUG

Listado 5 — Módulo compuesto por varios objetos.

Ciclo de prueba

make                         # produce hello.ko
modinfo hello.ko             # revisar metadatos y vermagic
sudo insmod ./hello.ko       # cargar
lsmod | grep hello           # confirmar
sudo dmesg -tH | tail -5     # leer los mensajes
sudo rmmod hello             # descargar
make clean

Listado 6 — Ciclo completo de compilación y prueba.

Los dos errores de carga más frecuentes:

  • Invalid module format — el vermagic no coincide con el kernel en ejecución. Suele pasar tras una actualización de kernel sin reiniciar, o al compilar contra los headers equivocados.
  • Operation not permitted — Secure Boot está activo y el módulo no está firmado. Ver la sección 10.

7. Parámetros y metadatos

Los parámetros permiten configurar el módulo al cargarlo y, si sus permisos lo autorizan, modificarlo en caliente a través de sysfs.

static int   veces  = 1;
static char *saludo = "hola";
static bool  ruidoso;
static int   lista[4];
static int   lista_n;

module_param(veces, int, 0644);
MODULE_PARM_DESC(veces, "Número de repeticiones");

module_param(saludo, charp, 0644);
MODULE_PARM_DESC(saludo, "Texto a imprimir");

module_param(ruidoso, bool, 0644);
MODULE_PARM_DESC(ruidoso, "Registro detallado");

module_param_array(lista, int, &lista_n, 0644);
MODULE_PARM_DESC(lista, "Hasta 4 enteros separados por comas");

/* uso: sudo insmod hello.ko veces=3 saludo="hey" lista=1,2,3 */
/* en caliente:                                               */
/*   cat /sys/module/hello/parameters/veces                   */
/*   echo 5 | sudo tee /sys/module/hello/parameters/veces      */

Listado 7 — Declaración de parámetros. El tercer argumento son los permisos del archivo en sysfs; 0 lo oculta.

Macros de metadatos que conviene conocer:

  • MODULE_ALIAS — nombre alternativo por el que modprobe puede encontrar el módulo.
  • MODULE_DEVICE_TABLE — publica los identificadores de hardware soportados; es lo que permite que udev cargue el driver automáticamente al conectar el dispositivo.
  • MODULE_SOFTDEP("pre: otro") — dependencia blanda: sugiere a modprobe cargar otro módulo antes o después.
  • MODULE_FIRMWARE — declara el blob de firmware que el módulo solicitará.

8. Character device completo

El character device es el driver más simple que expone una interfaz real al usuario: un nodo en /dev sobre el que funcionan open, read, write y close. El ejemplo siguiente es funcional en kernel 6.4 o superior.

/* midev.c — character device de eco, kernel 6.4+ */
#include <linux/module.h>
#include <linux/init.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/device.h>
#include <linux/uaccess.h>

#define NOMBRE  "midev"
#define TAM_BUF 256

static dev_t             dev_num;
static struct cdev       mi_cdev;
static struct class     *mi_clase;
static char              buf[TAM_BUF];
static size_t            usado;

static int mi_open(struct inode *inodo, struct file *f)
{
        pr_debug(NOMBRE ": open\n");
        return 0;
}

static int mi_release(struct inode *inodo, struct file *f)
{
        pr_debug(NOMBRE ": release\n");
        return 0;
}

static ssize_t mi_read(struct file *f, char __user *dst,
                       size_t len, loff_t *off)
{
        return simple_read_from_buffer(dst, len, off, buf, usado);
}

static ssize_t mi_write(struct file *f, const char __user *src,
                        size_t len, loff_t *off)
{
        if (len >= TAM_BUF)
                return -EINVAL;
        if (copy_from_user(buf, src, len))
                return -EFAULT;
        buf[len] = '\0';
        usado = len;
        return len;
}

static const struct file_operations mi_fops = {
        .owner   = THIS_MODULE,
        .open    = mi_open,
        .release = mi_release,
        .read    = mi_read,
        .write   = mi_write,
};

static int __init midev_init(void)
{
        int ret;

        ret = alloc_chrdev_region(&dev_num, 0, 1, NOMBRE);
        if (ret)
                return ret;

        cdev_init(&mi_cdev, &mi_fops);
        mi_cdev.owner = THIS_MODULE;
        ret = cdev_add(&mi_cdev, dev_num, 1);
        if (ret)
                goto err_region;

        mi_clase = class_create(NOMBRE);
        if (IS_ERR(mi_clase)) {
                ret = PTR_ERR(mi_clase);
                goto err_cdev;
        }

        if (IS_ERR(device_create(mi_clase, NULL, dev_num, NULL, NOMBRE))) {
                ret = -ENODEV;
                goto err_clase;
        }

        pr_info(NOMBRE ": listo en /dev/" NOMBRE " (major %d)\n",
                MAJOR(dev_num));
        return 0;

err_clase:
        class_destroy(mi_clase);
err_cdev:
        cdev_del(&mi_cdev);
err_region:
        unregister_chrdev_region(dev_num, 1);
        return ret;
}

static void __exit midev_exit(void)
{
        device_destroy(mi_clase, dev_num);
        class_destroy(mi_clase);
        cdev_del(&mi_cdev);
        unregister_chrdev_region(dev_num, 1);
        pr_info(NOMBRE ": descargado\n");
}

module_init(midev_init);
module_exit(midev_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Character device de eco");

Listado 8 — Character device completo, con manejo de errores en cascada mediante etiquetas goto: el patrón idiomático del kernel.

Prueba:

sudo insmod ./midev.ko
ls -l /dev/midev
echo "prueba" | sudo tee /dev/midev
sudo cat /dev/midev
sudo rmmod midev

Listado 9 — Verificación del dispositivo.

Dos detalles importantes. Los punteros marcados __user nunca se desreferencian directamente: se copian con copy_to_user / copy_from_user, que validan el acceso y pueden fallar. Y .owner = THIS_MODULE incrementa el contador de referencias mientras haya un descriptor abierto, lo que impide descargar el módulo con el dispositivo en uso.

9. Interfaces por /proc y /sys

procfs sirve para depuración rápida y salidas de texto libre; sysfs es la interfaz correcta para atributos de dispositivo, con la regla de un archivo, un valor.

/* procfs con seq_file */
#include <linux/proc_fs.h>
#include <linux/seq_file.h>

static int mi_show(struct seq_file *m, void *v)
{
        seq_printf(m, "contador=%d\nusado=%zu\n", contador, usado);
        return 0;
}

static int mi_proc_open(struct inode *i, struct file *f)
{
        return single_open(f, mi_show, NULL);
}

static const struct proc_ops mi_pops = {
        .proc_open    = mi_proc_open,
        .proc_read    = seq_read,
        .proc_lseek   = seq_lseek,
        .proc_release = single_release,
};

/* en init:  proc_create("midev", 0444, NULL, &mi_pops);  */
/* en exit:  remove_proc_entry("midev", NULL);            */

Listado 10 — Entrada en /proc usando la interfaz seq_file.

/* atributo de sysfs de lectura y escritura */
static ssize_t contador_show(struct device *d,
                             struct device_attribute *a, char *b)
{
        return sysfs_emit(b, "%d\n", contador);
}

static ssize_t contador_store(struct device *d,
                              struct device_attribute *a,
                              const char *b, size_t n)
{
        int ret = kstrtoint(b, 10, &contador);

        return ret ? ret : n;
}

static DEVICE_ATTR_RW(contador);

/* en init:  device_create_file(dev, &dev_attr_contador);  */
/* en exit:  device_remove_file(dev, &dev_attr_contador);  */

10. Depuración

Casi toda la depuración pasa por el búfer de mensajes del kernel. Los niveles, de mayor a menor urgencia: pr_emerg, pr_alert, pr_crit, pr_err, pr_warn, pr_notice, pr_info y pr_debug.

sudo dmesg -wH                    # seguir el log en vivo
sudo dmesg --level=err,warn       # filtrar por nivel
journalctl -k -b 0                # log del kernel del arranque actual
cat /proc/sys/kernel/tainted      # ¿el kernel está marcado?

# activar los pr_debug de un módulo sin recompilar
sudo mount -t debugfs none /sys/kernel/debug   # si no está montado
echo 'module midev +p' | sudo tee \
    /sys/kernel/debug/dynamic_debug/control

Listado 12 — Herramientas de observación y dynamic debug.

Ante un oops, lo útil es el call trace: la dirección donde falló y la pila de llamadas. scripts/decode_stacktrace.sh del árbol del kernel, o addr2line sobre el objeto con símbolos, convierten la dirección en archivo y línea. Para verificación estática y dinámica más profunda, el kernel ofrece sparse (make C=1), KASAN y lockdep, todos activables en un kernel de desarrollo.

11. Firma de módulos y Secure Boot

Con Secure Boot habilitado —el caso por defecto en muchos equipos con Pop!_OS— el kernel rechaza módulos sin una firma que pueda validar. La solución para desarrollo local es generar una clave propia, registrarla en el firmware como MOK (Machine Owner Key) y firmar cada módulo tras compilarlo.

mokutil --sb-state                # ¿Secure Boot activo?

# 1. generar el par de claves (una sola vez)
openssl req -new -x509 -newkey rsa:2048 -nodes -days 3650 \
  -outform DER -keyout MOK.priv -out MOK.der \
  -subj "/CN=Modulos locales/"
chmod 600 MOK.priv

# 2. registrar la clave pública en el firmware
sudo mokutil --import MOK.der     # pide una contraseña de un uso
sudo reboot                       # confirmar en MokManager al arrancar
mokutil --list-enrolled | grep -i "Modulos locales"

# 3. firmar el módulo después de cada compilación
sudo /usr/src/linux-headers-$(uname -r)/scripts/sign-file \
  sha256 MOK.priv MOK.der midev.ko

modinfo midev.ko | grep -E 'sig_id|signer|sig_key'

Listado 13 — Generación, registro y uso de una clave MOK.

La clave privada firma código que se ejecutará como kernel: guárdala con permisos 600, fuera de cualquier repositorio y fuera de copias de seguridad compartidas. DKMS puede firmar automáticamente en cada reconstrucción configurando mok_signing_key y mok_certificate en /etc/dkms/framework.conf.

12. Empaquetado con DKMS

Un módulo instalado a mano desaparece en la siguiente actualización de kernel. DKMS resuelve esto guardando el código fuente en /usr/src y recompilándolo automáticamente cada vez que se instala un kernel nuevo.

# dkms.conf, junto al código fuente
PACKAGE_NAME="midev"
PACKAGE_VERSION="1.0"
BUILT_MODULE_NAME[0]="midev"
DEST_MODULE_LOCATION[0]="/extra"
AUTOINSTALL="yes"
MAKE[0]="make -C ${kernel_source_dir} M=${dkms_tree}/${PACKAGE_NAME}/${PACKAGE_VERSION}/build modules"
CLEAN="make clean"

Listado 14 — dkms.conf mínimo. Con AUTOINSTALL="yes", cada kernel nuevo dispara la reconstrucción.

sudo cp -r . /usr/src/midev-1.0
sudo dkms add     -m midev -v 1.0
sudo dkms build   -m midev -v 1.0
sudo dkms install -m midev -v 1.0
dkms status
sudo modprobe midev

# desinstalar
sudo dkms remove -m midev -v 1.0 --all
sudo rm -rf /usr/src/midev-1.0

Listado 15 — Ciclo de instalación y desinstalación con DKMS.

Para que el módulo se cargue en cada arranque, basta un archivo con su nombre en /etc/modules-load.d/midev.conf, y sus opciones por defecto en /etc/modprobe.d/midev.conf con la línea options midev veces=3.

13. Seguridad y hardening

La carga de módulos es la vía más directa a ejecución arbitraria en anillo 0, así que en sistemas de producción se restringe:

Control Efecto
module.sig_enforce=1 Rechaza todo módulo sin firma válida, incluso con Secure Boot desactivado.
kernel.modules_disabled=1 Congela la carga y descarga de módulos hasta el próximo reinicio. Irreversible en caliente.
lockdown=integrity Bloquea las vías por las que root podría modificar el kernel en ejecución.
blacklist <mod> En /etc/modprobe.d/: impide la carga automática. Para bloquearla del todo: install <mod> /bin/false.
CONFIG_MODULES=n Kernel sin soporte de módulos: la opción más estricta, requiere compilación propia.

Dentro del código, la higiene mínima:

  • Validar longitudes y rangos de toda entrada de usuario antes de copiar.
  • No asumir que los datos que llegan de espacio de usuario terminan en '\0'.
  • Comprobar privilegios con capable(CAP_SYS_ADMIN) en las operaciones sensibles, no con el UID.
  • No filtrar direcciones del kernel en los mensajes de log: usar %p, que las ofusca.
  • Proteger el estado compartido con mutex o spinlock según el contexto; nunca dormir dentro de un spinlock.

14. Lista de verificación

  • Cada recurso reservado en init se libera en exit, en orden inverso.
  • Se revisa el valor de retorno de todo registro, con salida en cascada por etiquetas.
  • Ningún puntero __user se desreferencia directamente.
  • No hay buffers grandes en la pila; lo grande va a kmalloc.
  • No se duerme en contexto atómico ni con un spinlock tomado.
  • Se ejecutó depmod -a tras modules_install.
  • El módulo se compiló contra los headers del kernel en ejecución.
  • Las pruebas se hacen en una máquina virtual, no en el equipo de trabajo.
