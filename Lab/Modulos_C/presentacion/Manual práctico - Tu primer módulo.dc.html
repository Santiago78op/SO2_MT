Manual práctico: tu primer módulo

Bitácora del laboratorio hola_santiago.ko · de la carpeta vacía al módulo cargado

Pop!_OS · kernel 6.17.9-76061709-generic · complemento de «Referencia — Módulos del kernel Linux»

Este manual documenta, paso por paso, el laboratorio completo: los siete pasos que van de una carpeta vacía a un módulo cargado y descargado del kernel. A diferencia de la Referencia, que es teórica y de consulta, acá está el camino recorrido con los comandos exactos, la salida real que produce cada uno, y los errores que aparecieron de verdad.

La sección 4 es la más importante para crecer: explica cómo se declara un módulo cuando su código está en uno o en varios archivos, y cómo se construyen varios módulos desde un mismo Makefile.

1. Paso 0 — Revisar el terreno

Un módulo no se compila con un compilador cualquiera: se compila contra los headers de la versión exacta del kernel que está corriendo. Sin esos headers, nada de lo que sigue funciona, y el error que produce make no lo explica con claridad. Conviene descubrirlo antes de escribir código.

uname -r
test -d /lib/modules/$(uname -r)/build && echo "HEADERS: OK" || echo "HEADERS: FALTAN"
gcc --version | head -1
make --version | head -1

Listado 1 — Verificación del entorno de compilación.

Si los headers faltan, se instalan según la distribución:

# Pop!_OS / Ubuntu / Debian / Mint
sudo apt update && sudo apt install build-essential linux-headers-$(uname -r)

# Fedora / RHEL
sudo dnf install kernel-devel kernel-headers gcc make

# Arch / Manjaro
sudo pacman -S base-devel linux-headers

Listado 2 — Instalación de headers y herramientas de compilación.

El valor que devuelve uname -r es la referencia de todo el proceso. Queda grabado dentro del módulo compilado como vermagic, y al cargarlo el kernel compara esa cadena contra la suya. Si difieren, rechaza el módulo.

2. Paso 1 — Anatomía del módulo mínimo

Un módulo no es un programa: no tiene main(). Tiene dos funciones que el kernel invoca, una al cargarlo y otra al descargarlo. Entre esos dos momentos el módulo no ejecuta nada: queda residente, esperando que algo lo despierte.

/*
 * hola_santiago.c - Mi primer modulo del kernel Linux.
 */

#include <linux/module.h>
#include <linux/init.h>
#include <linux/printk.h>

/* Se ejecuta cuando CARGO el modulo */
static int __init hola_init(void)
{
    pr_info("Hola, Santiago Barrera - Carnet 201905884\n");
    return 0;
}

/* Se ejecuta cuando DESCARGO el modulo */
static void __exit hola_exit(void)
{
    pr_info("Adios, Santiago Barrera - Carnet 201905884\n");
}

module_init(hola_init);
module_exit(hola_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Santiago Barrera - 201905884");
MODULE_DESCRIPTION("Mi primer modulo: saluda al cargar y al descargar");
MODULE_VERSION("1.0");

Listado 3 — hola_santiago.c completo.

Qué significa cada elemento

Elemento Para qué sirve
<linux/…> Headers del kernel. La biblioteca estándar de C no existe en este entorno: no hay stdio.h ni stdlib.h.
static Impide que el símbolo se exporte a la tabla global del kernel, donde competiría con los de miles de módulos. Regla: todo static salvo lo que se exporte a propósito con EXPORT_SYMBOL().
__init Coloca la función en una sección especial que el kernel libera de memoria después de ejecutarla. Solo válido para código que nunca se vuelve a llamar.
__exit Si el módulo se compila dentro del kernel (no cargable), esta función es inalcanzable y el enlazador la descarta.
pr_info() El equivalente de printf. No escribe en ninguna terminal: escribe en el búfer circular del kernel, que se lee con dmesg.
return 0 Contrato con insmod: cero significa aceptado. Un negativo (-ENOMEM, -EINVAL) aborta la carga. Nunca se devuelven positivos ni códigos propios.
module_init / module_exit El registro. Los nombres de las funciones son libres; estas dos macros son las que le dicen al kernel cuál es cuál. Sin ellas el módulo compila, carga y no hace nada.
MODULE_LICENSE Obligatorio, y con efecto técnico: sin una licencia compatible con GPL el kernel se marca como contaminado y el módulo pierde acceso a los símbolos exportados con EXPORT_SYMBOL_GPL().

Regla que se olvida con frecuencia: si la función de inicialización falla, debe dejar el sistema exactamente como lo encontró. Cuando init devuelve un error, el kernel no llama nunca a la función de salida. Si se registraron tres recursos y el cuarto falla, hay que liberar los tres antes de retornar.

3. Paso 2 — El Makefile

El código de un módulo no se compila con gcc a mano. Tiene que compilarse con el mismo compilador, las mismas banderas y los mismos headers con los que se construyó el kernel en ejecución. Quien lo hace es el sistema de construcción del propio kernel, Kbuild. El Makefile del módulo no compila: delega.

obj-m += hola_santiago.o

KDIR ?= /lib/modules/$(shell uname -r)/build
PWD  := $(CURDIR)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Listado 4 — Makefile completo. Las dos líneas de receta están indentadas con TABULADOR.

El Makefile se lee dos veces

Esta es la parte que confunde, y entenderla ahorra horas:

  • Primera lectura — al ejecutar make: se interpreta como un Makefile normal y se ejecuta la receta all, que se traslada con -C al árbol del kernel.
  • Segunda lectura — el árbol del kernel vuelve con M=<carpeta> y Kbuild lee el mismo archivo, pero esta vez solo le interesan las líneas obj-m.
Fragmento Significado
obj-m Palabra reservada de Kbuild, no se puede renombrar. La m significa «como módulo cargable». Con obj-y el código iría compilado dentro del kernel.
?= Asigna solo si la variable no viene definida desde afuera. Permite make KDIR=/otra/ruta para compilar contra otro kernel sin editar el archivo.
:= Asignación inmediata: se evalúa una sola vez. Con = se reevaluaría cada vez que se usa la variable.
$(MAKE) El mismo make que está ejecutando. Más robusto que escribir make: propaga opciones como -j8.
M=$(PWD) Le indica al árbol del kernel dónde está el código externo. CURDIR es la variable de make con el directorio actual.
all / clean Convenciones, no obligaciones. all es lo que corre make sin argumentos. KDIR y PWD también son nombres libres.

El TABULADOR y el error «missing separator»

Las líneas de receta deben empezar con un TABULADOR real, y el TABULADOR debe ser el primer carácter de la línea. Un solo espacio antes de él rompe la compilación con un mensaje que no menciona la indentación:

Makefile:7: *** missing separator.  Stop.

Listado 5 — El error más frecuente al escribir un Makefile a mano.

Para make, cada línea debe ser una asignación de variable, un encabezado de receta, o un comando indentado con TABULADOR. Cuando no encaja en ninguna, informa que falta el separador. La verificación se hace con caracteres visibles:

$ cat -A Makefile | nl -ba
     1  obj-m += hola_santiago.o$
     2  $
     3  KDIR ?= /lib/modules/$(shell uname -r)/build$
     4  PWD  := $(CURDIR)$
     5  $
     6  all:$
     7  ^I$(MAKE) -C $(KDIR) M=$(PWD) modules$

# $   = fin de linea
# ^I  = TABULADOR  <- debe estar pegado al margen izquierdo
#       si aparece "  ^I" con espacios delante, ahi esta el error

Listado 6 — cat -A revela los caracteres invisibles; nl -ba numera igual que make.

Muchos editores convierten el TABULADOR en espacios sin avisar. En nano se desactiva así, una sola vez:

echo 'unset tabstospaces' >> ~/.nanorc
echo 'unset autoindent'   >> ~/.nanorc

Listado 7 — Configurar nano para que escriba TABULADORES reales.

Alternativa infalible: generar el archivo con printf, donde el \t produce un TABULADOR verdadero y no depende del editor:

printf 'obj-m += hola_santiago.o\n\nKDIR ?= /lib/modules/$(shell uname -r)/build\nPWD  := $(CURDIR)\n\nall:\n\t$(MAKE) -C $(KDIR) M=$(PWD) modules\n\nclean:\n\t$(MAKE) -C $(KDIR) M=$(PWD) clean\n' > Makefile

4. Uno o varios archivos, uno o varios módulos

Kbuild distingue tres situaciones, y confundirlas produce errores difíciles de leer. La clave está en entender que obj-m declara módulos resultantes, no archivos fuente.

4.1 Un módulo desde un solo archivo

El caso simple, y el único que no necesita declaración adicional:

obj-m += hola_santiago.o

Kbuild lee hola_santiago.o, deduce que el fuente es hola_santiago.c, lo compila y produce hola_santiago.ko. Nombre del objeto, nombre del fuente y nombre del módulo coinciden.

4.2 Un módulo desde varios archivos

Cuando el módulo crece se parte en varios .c, pero el resultado sigue siendo un solo .ko. Kbuild ya no puede deducir nada: hay que declararle las piezas.

obj-m         += startstop.o
startstop-objs := start.o stop.o

Listado 9 — Módulo compuesto, tomado de los ejemplos del LKMPG.

El detalle que explica la necesidad de esa segunda línea: en esa carpeta no existe ningún startstop.c. Solo hay start.c (que aporta la entrada) y stop.c (que aporta la salida). Ninguno es un módulo completo por separado. Sin la línea -objs, Kbuild buscaría startstop.c y fallaría.

La regla, con su restricción de nombres:

obj-m                    += <nombre-modulo>.o
<nombre-modulo>-objs     := pieza1.o pieza2.o pieza3.o

# El prefijo debe coincidir EXACTO con el nombre puesto en obj-m.
# startstop.o  ->  startstop-objs     correcto
#              ->  start-stop-objs    ignorado silenciosamente
#              ->  startstop_objs     ignorado silenciosamente

Listado 10 — Forma general y errores de nomenclatura.

Kbuild compila cada pieza por separado y las enlaza en un único .ko. Es la misma idea que gcc a.c b.c -o programa en espacio de usuario, con la diferencia de que acá hay que declararlo explícitamente.

Consideraciones al partir un módulo en varios archivos:

  • Un solo module_init y un solo module_exit en todo el conjunto, no uno por archivo.
  • Las macros MODULE_* van una sola vez. Si se repite MODULE_LICENSE en dos archivos, el enlazado falla por símbolo duplicado.
  • Las funciones y variables que se comparten entre piezas no pueden ser static, y se declaran en un header propio del módulo.
  • Ninguna pieza puede llamarse igual que el módulo. Un startstop-objs := startstop.o start.o entra en un conflicto circular.
  • La forma moderna, preferida hoy dentro del árbol del kernel, es <nombre>-y := …. Ambas funcionan; -objs es la clásica y la que usa el LKMPG.

4.3 Varios módulos desde un mismo Makefile

Un Makefile puede construir tantos módulos independientes como se quiera: basta una línea obj-m por módulo. Cada una produce su propio .ko, que se carga y descarga por separado. Así está armado el Makefile de los ejemplos del LKMPG, con más de cuarenta módulos:

obj-m += hello-1.o
obj-m += hello-2.o
obj-m += hello-5.o
obj-m += startstop.o          # este es compuesto...
startstop-objs := start.o stop.o
obj-m += chardev.o
obj-m += procfs1.o

KDIR ?= /lib/modules/$(shell uname -r)/build

all:
	$(MAKE) -C $(KDIR) M=$(CURDIR) modules

Listado 11 — Varios módulos independientes, uno de ellos compuesto, en un solo Makefile.

Un solo make construye todos. Para trabajar sobre uno solo durante el desarrollo, se puede pedir su objeto por nombre: make -C $KDIR M=$PWD hello-1.ko. Y como obj-m usa +=, el orden de las líneas es irrelevante: se acumulan en una lista.

4.4 Resumen de los tres casos

Situación Declaración Resultado
1 módulo, 1 archivo obj-m += a.o a.ko
1 módulo, N archivos obj-m += a.o
a-objs := x.o y.o		 a.ko (uno solo)
N módulos obj-m += a.o
obj-m += b.o		 a.ko y b.ko

5. Paso 3 — Compilar

La salida de make muestra el Makefile funcionando:

make -C /lib/modules/6.17.9-76061709-generic/build M=/home/santiago/mi_primer_modulo modules
make[1]: Entering directory '/usr/src/linux-headers-6.17.9-76061709-generic'
  CC [M]  hola_santiago.o
  MODPOST Module.symvers
  CC [M]  hola_santiago.mod.o
  LD [M]  hola_santiago.ko
make[1]: Leaving directory '/usr/src/linux-headers-6.17.9-76061709-generic'

Listado 12 — Salida de una compilación exitosa.

Etapa Qué ocurre
Entering directory La delegación: make se traslada al árbol del kernel.
CC [M] Compilación del fuente. La marca [M] significa «como módulo», y viene de obj-m.
MODPOST Etapa propia del kernel: verifica que todos los símbolos usados existan y genera el código de pegamento con los metadatos. Es la razón por la que no sirve gcc a secas.
LD [M] Enlazado final. Produce el .ko, que es el módulo.

Advertencias habituales que no son errores: Skipping BTF generation … due to unavailability of vmlinux (falta información para herramientas de trazado) y avisos de que el compilador difiere del que construyó el kernel. Si la última línea es LD [M] … .ko, la compilación salió bien.

Antes de cargarlo conviene revisar los metadatos, que ya están dentro del binario:

$ modinfo hola_santiago.ko
filename:       /home/santiago/mi_primer_modulo/hola_santiago.ko
version:        1.0
description:    Mi primer modulo: saluda al cargar y al descargar
author:         Santiago Barrera - 201905884
license:        GPL
vermagic:       6.17.9-76061709-generic SMP preempt mod_unload modversions

Listado 13 — Los metadatos declarados en el fuente, ya grabados en el módulo.

6. Paso 4 — Cargar

sudo insmod hola_santiago.ko     # no imprime nada: el silencio es exito
sudo dmesg | tail -5             # el mensaje esta aca
sudo dmesg -T | tail -5          # con fecha y hora legibles

Listado 14 — Carga del módulo y lectura del log del kernel.

La terminal no responde nada al cargar el módulo, y eso es el comportamiento correcto: en Unix el silencio indica éxito. El mensaje de pr_info está en el búfer del kernel, no en la terminal.

Secuencia interna de lo que hace el kernel en ese instante:

  1. insmod lee el archivo y lo entrega por la llamada al sistema finit_module.
  2. Compara el vermagic del módulo con el suyo.
  3. Verifica que todos los símbolos externos existan, según lo preparado por MODPOST.
  4. Reserva memoria, copia el código y ajusta las direcciones (reubicación).
  5. Llama a la función registrada con module_init.
  6. Si devolvió cero, deja el módulo residente y libera la memoria de la función __init, que ya no se volverá a usar.

Para desarrollo conviene dejar el log abierto en una segunda terminal, de modo que los mensajes aparezcan en el momento:

sudo dmesg -wH        # -w = seguir en vivo, -H = legible. Ctrl-C para salir

Listado 15 — Monitoreo continuo del log del kernel.

7. Paso 5 — Inspeccionar el módulo cargado

$ lsmod | grep hola_santiago
hola_santiago          12288  0
#      nombre          bytes  contador de referencias

$ grep hola_santiago /proc/modules
hola_santiago 12288 0 - Live 0xffffffffc0d5a000 (OE)

Listado 16 — lsmod es un formateador de /proc/modules, que es la fuente cruda.

La tercera columna es el contador de referencias: mientras no sea cero, el kernel se niega a descargar el módulo. En la fuente cruda aparece además el estado (Live), la dirección de memoria del kernel donde reside el código, y las banderas de contaminación.

Las banderas (OE) y el kernel contaminado

Al cargar un módulo propio, el log muestra dos avisos que no son fallas:

hola_santiago: loading out-of-tree module taints kernel.
hola_santiago: module verification failed: signature and/or required key
               missing - tainting kernel

Listado 17 — Avisos de contaminación al cargar un módulo externo sin firmar.

  • O — out-of-tree: el módulo no forma parte del código oficial del kernel.
  • E — el módulo no está firmado criptográficamente.

Un kernel «contaminado» declara que cargó código que no controla; los desarrolladores del kernel descartan reportes de fallas en ese estado. El estado global se lee en /proc/sys/kernel/tainted y no se limpia al descargar el módulo: persiste hasta reiniciar. Si MODULE_LICENSE no fuera compatible con GPL, aparecería una tercera bandera y el módulo perdería acceso a la mayoría de las funciones del kernel.

El directorio en sysfs

Al cargar el módulo, el kernel crea sin intervención un directorio con su estado:

ls  /sys/module/hola_santiago/
cat /sys/module/hola_santiago/refcnt        # 0     contador de referencias
cat /sys/module/hola_santiago/initstate     # live  estado
cat /sys/module/hola_santiago/coresize      # bytes en memoria
cat /sys/module/hola_santiago/version       # 1.0   viene de MODULE_VERSION
cat /sys/module/hola_santiago/taint         # OE

Listado 18 — Estado del módulo expuesto en sysfs.

Un módulo sin parámetros declarados no tiene el subdirectorio parameters/. Aparece solo en cuanto se declara el primer module_param con permisos distintos de cero, y desde ahí se pueden leer —y según los permisos, modificar en caliente— los valores del módulo cargado.

Dos fuentes de información distintas

Herramienta Consulta Requiere
modinfo x.ko el archivo en disco que exista el archivo; el módulo puede estar descargado
lsmod · /proc/modules · /sys/module el kernel en ejecución que el módulo esté cargado

8. Paso 6 — Descargar

sudo rmmod hola_santiago     # SIN la extension .ko
sudo dmesg | tail -3         # aparece el mensaje de salida
make clean                   # borra los archivos generados

Listado 19 — Descarga y limpieza.

La asimetría entre los dos comandos no es capricho sintáctico: insmod recibe la ruta de un archivo, porque el módulo todavía no existe para el kernel; rmmod recibe un nombre, porque el módulo ya vive dentro del kernel registrado con ese nombre. El archivo podría haberse borrado del disco y la descarga funcionaría igual.

Lo que hace el kernel al descargar:

  1. Revisa el contador de referencias. Si no es cero, se niega.
  2. Llama a la función registrada con module_exit.
  3. Libera la memoria del código y elimina la entrada de /proc/modules y el directorio de /sys/module/.

Existe también modprobe -r, que además descarga dependencias que hayan quedado sin uso. Para desarrollo, rmmod es más directo y predecible.

9. Errores y su causa

Mensaje Causa y solución
missing separator Espacios en lugar de TABULADOR en una receta, o espacios antes del TABULADOR. Verificar con cat -A.
No rule to make target … modules Faltan los headers del kernel, o KDIR apunta a una ruta inexistente.
No such file or directory: x.c Un obj-m nombra un objeto sin fuente. Si el módulo es compuesto, falta la línea -objs (o su prefijo no coincide).
Invalid module format El vermagic no coincide con el kernel en ejecución. make clean && make; el detalle está en dmesg.
Key was rejected by service Secure Boot activo y módulo sin firmar. Comprobar con mokutil --sb-state: hay que firmarlo o desactivar Secure Boot.
Operation not permitted Falta sudo, o la carga de módulos está bloqueada (kernel.modules_disabled=1).
File exists El módulo ya está cargado de un intento anterior. Descargarlo primero.
Module x is in use Contador de referencias distinto de cero. Ver la columna Used by de lsmod.
Unknown symbol in module Se usa un símbolo no exportado, o falta cargar antes otro módulo. El detalle exacto está en dmesg.
El módulo carga pero no imprime nada Faltan module_init / module_exit, o el mensaje se busca en la terminal en vez de dmesg.

10. El ciclo de trabajo completo

make                              # compilar  -> hola_santiago.ko
modinfo hola_santiago.ko          # revisar metadatos y vermagic
sudo insmod hola_santiago.ko      # cargar
lsmod | grep hola_santiago        # confirmar que esta residente
sudo dmesg | tail                 # observar la salida
sudo rmmod hola_santiago          # descargar  (sin .ko)
sudo dmesg | tail                 # confirmar el mensaje de salida
make clean                        # limpiar

Listado 20 — El bucle que se repite en todo el desarrollo de módulos.

Lista de verificación

  • Headers instalados y coincidentes con uname -r.
  • module_init y module_exit presentes, una sola vez cada uno.
  • MODULE_LICENSE("GPL") declarado.
  • Todo símbolo interno marcado static.
  • La función de inicialización libera lo que registró si falla, y devuelve un error negativo.
  • Todo lo creado en init se destruye en exit, en orden inverso.
  • Recetas del Makefile indentadas con TABULADOR (verificado con cat -A).
  • Si el módulo es compuesto, la línea -objs con el prefijo exacto, y ninguna pieza con el nombre del módulo.
  • Las pruebas, en una máquina virtual o de laboratorio. Un módulo con errores no da un mensaje: congela el sistema.
